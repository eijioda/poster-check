## 2. 2つの使われ方

### ① ディレクターモード（**先に作る**）

```
アミーゴがLINEでポスター画像を送ってくる
   ↓
ディレクターがアプリに貼る（LINEで受け取った画像を選ぶ／PCならCtrl+V）
   ↓
AIチェック（約30秒）
   ↓
伝える指摘を選ぶ・並べ替える          ← ここが人の仕事
   ↓
FB文をつくる（2秒）→ 手直し
   ↓
LINEに貼って送る
```

ディレクターの困りごと:

| やりたいこと | いま |
|-------------|------|
| **指摘をもとに、アミーゴに送るLINE文を作りたい** | ✗ 手で書いている |
| 言い方をやわらかく／厳しくしたい | ✗ |
| **伝えなくていい指摘を落としたい** | ✗ AIの指摘が全部出る |
| **どれから直してほしいか、順番を示したい** | ✗ |
| 長すぎるLINEにしたくない | ✗ |
| いま動いている企画の全体像を見たい | ✗ |

**端末: スマホ（現場・LINEを見ながら）＋PC（事務作業）。両方。**
画像の入口は「**アルバムから選ぶ**」と「**貼り付け**」が主。撮影は副。

### ② アミーゴ壁打ちモード（次に作る）

アプリを中高生本人に渡して、自分で直してもらう使い方。

| やりたいこと | いま |
|-------------|------|
| 何をどう直せばいいか、手順で知りたい | △ 指摘は出るが消し込めない・コピーできない |
| 直したらもう一度見て、直ったか確かめたい | △ 前回との比較がない |
| 直し終わったらディレクターに見てもらう | △ 共有リンクはあるが送る導線がない |

**端末: ほぼスマホ。** 画像の入口は「**撮影**」と「**スクショ**」が主。

> 同じチェックエンジンを、包み方だけ変えて出す。AIへの投げ方は共通、
> **出し方（言葉づかい・並べ方・次の一手）だけが違う。**

## 5. FB文の設計（中心）

### 5-1. つくり方

チェック結果（`summary` / `passed` / `findings`）はサーバに保存済み（`checkStore.js`）。
**画像を送り直さず、保存済みJSONだけを材料にテキスト生成する。**

```
[チェック] ──> /api/check ──> 画像＋ルール → GPT（30秒・数円）
                                  └→ checkStore に保存（shareId）
                                              │
[FB文]  ──> /api/feedback ──> 保存済みJSON＋設定 → GPT（2秒・0.1円未満）
                ↑                                    │
                └── 言い方・長さを変えて作り直す ←───┘
```

チェックの中で同時に作ると、作り直すたびに30秒と数円かかる。**必ず分ける。**

### 5-2. 入力

```jsonc
POST /api/feedback
{
  "checkId": "xYz123abc",
  "to": "さくら",
  "projectName": "古着リメイク市",
  "deadline": "9/26(金)",
  "order": [1, 0, 2, 4],     // 伝える指摘を「送る順」に並べたindex（外したものは含めない）
  "mustFixCount": 2,         // 先頭から何件を「まず直す」にするか
  "tone": "gentle",          // gentle | normal | firm
  "length": "normal",        // short | normal | long
  "withLink": true
}
```

`include`（選択）と並び順を **`order` 1本にまとめた**。配列の順＝送る順、
先頭 `mustFixCount` 件が「まず直す」。UIの↑↓と線の位置がそのまま入る。

### 5-3. 出力

```jsonc
{
  "message": "（そのままLINEに貼れる本文）",
  "messages": ["1通目…", "2通目…"],   // 「2通に分ける」を押したとき
  "parts": {
    "greeting": "さくらさん、ポスターありがとう！",
    "good": ["日時と会場がはっきり書けていて分かりやすい"],
    "mustFix": [
      { "no": 1, "title": "終わりの時刻", "how": "開始時刻の右に足す", "example": "10:00〜12:00" },
      { "no": 2, "title": "駐車場の場所", "how": "会場の住所の下に1行足す", "example": "駐車場: 旧五十沢中学校グラウンド" }
    ],
    "niceToHave": [
      { "no": 3, "title": "企画名に一言そえる", "how": "体験なのか販売なのかが分かるように" }
    ],
    "closing": "9/26(金)までに直してもらえると助かります！"
  },
  "charCount": 284,
  "costYen": 0.06
}
```

### 5-4. 長さと優先順位（ここが連動する）

**長さを短くする＝優先順位の低い指摘を落として、リンクに逃がす。**
これを規則として決めておく。

| 長さ | FB文に入れるもの | 目安 | LINEでの見え方 |
|------|-----------------|------|---------------|
| **短め** | 「まず直す」の**上位2件だけ**。残りは「ほかにも気づいた点はリンクを見てね」 | 150字前後 | 1画面に収まる |
| **ふつう** | 「まず直す」全部 ＋「余裕があれば」1件 | 300字前後 | 2〜3画面 |
| **くわしい** | 全部 ＋ なぜ直すか（読み手がどう困るか）まで | 500字前後 | 長い。2通に分けるのを勧める |

**優先順位の付け方**
- 初期値は `❌ error → ⚠️ warning → 💡 suggestion` の順。同じ重要度の中では
  「参加者・保護者が実際に困る度合い」が大きい順（例: 終了時刻 > 改行位置）
- 「まず直す／余裕があれば」の境界の初期値は **❌と⚠️の間**
- ディレクターが ↑↓ と境界線で自由に変えられる。**AIの順番を鵜呑みにさせない**

**本文での出し方**

```
まず直してほしいところ
① 終わりの時刻
② 駐車場の場所

余裕があれば
③ 企画名に一言そえる
```

短めのときは「まず直してほしい」だけを出し、③以降は
「ほかにも細かい点をいくつか見つけたので、よかったらこちらも → (リンク)」に置き換える。

### 5-5. プロンプトの方針

```
あなたは南魚沼市 mirai塾のディレクターです。
中高生（アミーゴ）が作ったポスターへの指摘を、本人に LINE で送る
メッセージに書き直してください。

# 大原則
- 相手は中学生・高校生。萎縮させない。ダメ出しの列挙にしない
- 「よかったところ」→「まず直してほしいところ」→「余裕があれば」→「ひとこと」
- 直してほしいところは、必ず **どう直すか（そのまま使える具体案）** まで書く
- 「〜してください」より「〜してもらえると助かります」
- 渡された指摘だけを使う。順番も渡されたとおりに、①②③と番号をふる
- ポスターを直接見ていないことを匂わせる表現は書かない

# 言い方（tone）
- gentle … 初めて／1年生向け。クッションを厚く。必須だけ伝える
- normal … ふだん
- firm  … 公開直前。期限を明確に。ただし人格には触れない

# 長さ（length）
- short  … 150字前後。まず直す上位2件のみ。残りはリンクへ逃がす
- normal … 300字前後
- long   … 500字前後。なぜ直すか（誰がどう困るか）まで書く

# LINE向けの書き方
- 改行を多めに。1段落は2〜3行まで
- 絵文字は控えめ（0〜2個）。①②③の丸数字は積極的に使う
- 箇条書きの記号は「・」より「①②③」。LINEで崩れにくい
- URLは行の先頭に単独で置く（自動リンクが切れないため）
- 件名・あいさつ定型（お疲れさまです等）は書かない。LINEなので用件から
```

### 5-6. 文例（tone=gentle / length=normal）

```
さくらさん、ポスターありがとう！

日時と会場がはっきり書いてあって、ぱっと見て分かりやすかったです◎
イラストもかわいい！

公開する前に、2つだけ直してほしいところがあります。

① 終わりの時刻
「10:00〜」だけだと何時に終わるか分からなくて、
保護者の方が予定を立てにくいです。
→ 10:00〜12:00

② 駐車場の場所
会場の住所の下に1行足してもらえますか。
→ 駐車場: 旧五十沢中学校グラウンド

余裕があれば、企画名に短い説明があるともっと伝わります。
「古着リメイク市」だけだと、自分で作る体験なのか、
買えるお店なのか迷うかも。

9/26(金)までに直してもらえると助かります。
分からないところがあったら聞いてね！
```

### 5-7. 伝えない指摘を落とせること

AIは 💡改善提案 を拾いすぎる。全部送ると中高生には「ダメ出しの山」に見える。

**送る前の初期値:**

| 重要度 | 初期状態 | 位置 |
|--------|---------|------|
| ❌ error | ON | まず直す |
| ⚠️ warning | ON | まず直す |
| 💡 suggestion | **OFF** | （足すと「余裕があれば」へ） |

## 6. モードの切り替え

ログイン機構は入れない。「ログイン不要」という今の良さを壊さないため。

| 案 | 内容 | 評価 |
|----|------|------|
| **A. 合言葉（推奨）** | 管理タブを開くと合言葉を1回聞く。合えば端末に記憶。環境変数 `DIRECTOR_PASSCODE` | ○ 軽い・既存の思想に合う |
| B. URLを知っている人だけ | `/admin` を知っていれば誰でも | △ 履歴が全部見えるので弱い |
| C. ログイン（NextAuth等） | | ✗ 人数に対して重すぎる |

**A を推奨。** 合言葉はディレクター間で共有、半年に一度変える運用で足りる。
アミーゴに渡すときは合言葉を教えなければ、そのまま②壁打ちモードになる。

## 7. 「全体像」を、管理画面を作らずに出す

### 7-1. 何が問題だったか

いまの保存は **IDを知らないと何も取り出せない**。

```js
createCheck(data) → { id, ... }   // 作る
getCheck(id)      → record        // IDを知っていれば読める
// ↑ 一覧を返す関数がない
```

ちゃんとした管理画面を作るなら、企画(project)モデル＋インデックス＋
状態遷移が要る（2〜3日）。**そこまでやらずに「全体像」を出す道を2本用意する。**

> ⚠️ Redis の `KEYS` で代用するのは不可。Upstash無料枠で遅く、非推奨。

### 7-2. 道その1: ディレクターの端末内に履歴を貯める（すぐできる）

ディレクターは数人。基本は同じ端末を使う。**サーバに一覧を持たなくても足りる。**

```js
// localStorage: "poster-check:history"
[
  { checkId, projectName, amigo, at, counts: {e:2,w:3,s:1}, fbSentAt: null },
  ...
]
```

- チェックすると1件積まれる
- FB文をコピーすると `fbSentAt` が入り、「🔴FB未送信 → 🟢送信済み」に変わる
- 管理タブはこれを並べるだけ。**新しいAPIもストアも要らない**

制約: 端末を変えると見えない。共有もできない。→ 道その2で補う。

### 7-3. 道その2: 既存のスプレッドシート連携に相乗りする（推奨）

**すでにある仕組みを使う。** `lib/sheets.js` がアンケート作成時に
Apps Script（`SHEETS_WEBHOOK_URL`）へ行を投げている。
**ここにチェック結果の行も足すだけ**で、全体像はスプレッドシートで見られる。

```js
// チェック完了時に1行追記
{
  種別: "ポスターチェック",
  ワークショップ名: "古着リメイク市",
  作成者名: "さくら",            // ＝アミーゴ名
  必須欠落: 2, 要確認: 3, 改善提案: 1,
  FB送信: "",                     // FB文コピー時に別途更新 or 手で
  添削url: "https://…/c/xYz123abc",
}
```

**利点**
- アプリ内に管理画面を作らなくていい。実装は `sheets.js` の呼び出し1か所追加
- ディレクター同士で共有できる（端末を選ばない）
- 並べ替え・絞り込み・メモ書きはスプレッドシートのほうが得意
- アンケートの行と同じシートに並ぶので、**企画の全体像が自然に1枚になる**

**制約**
- アプリ内から読み戻せない（Apps Scriptは `doPost` のみ）。読み戻したくなったら
  `doGet` を足す（SETUP_SHEETS.md のスクリプトに10行ほど追記）

### 7-4. 将来案: 企画(project)モデル（いまは作らない）

7-2・7-3で足りなくなったら着手する。

project（企画）

## 9. スマホ操作性の基準

| 項目 | 基準 | なぜ |
|------|------|------|
| タブの高さ | 56px ＋ `env(safe-area-inset-bottom)` | iPhoneのホームバーに隠れない |
| `main` の下余白 | 現状96px → **タブ分 +64px** | 最後の要素がタブに隠れる事故を防ぐ |
| タップ領域 | 最低 44×44px | 現状 `.mini-copy` は34〜40px程度で、指が太いと外す |
| 入力欄の文字 | **16px以上** | iOS Safariの自動ズーム防止（現状 `.rule-input` は 0.95rem≒15.2px で**ズームする**） |
| 主ボタン | 画面下に sticky | 長い結果を見たあと上に戻らず押せる |
| ポスタープレビュー | `max-height: 55vh` | 現状340px固定。縦長ポスターが潰れる |
| FB文の編集欄 | 最低8行・自動伸長 | スマホで全文が見えないと手直しできない |
| 横スクロール | 禁止 | `.script-box`（黒いコード欄）は折りたたみへ |
| QRコード | 折りたたみ | 使うのは印刷時だけ。常時156px占有は重い |
| 画像の入口 | モードで変える | ディレクター=アルバム/貼り付け優先、アミーゴ=撮影優先 |

配色・トーンは `app/globals.css` の Nova デザインシステムのまま。**変えない。**

## 10. 実装フェーズ

**ディレクター用を先に、が決定事項。** それに合わせて組み替えた。

| Phase | 内容 | 目安 | 効果 |
|-------|------|------|------|
| **0** | この設計書のレビュー | — | ← いまここ |
| **1** | **FB文の生成**（`/api/feedback` ＋ 指摘の選択・並べ替え・tone/長さ ＋ コピー） | 1〜1.5日 | **ディレクターの手書きが消える。ここが一番効く** |
| **2** | 下タブ導入・画面3分割・スマホ基準の適用・画像の貼り付け対応 | 1〜2日 | 現場で使える形になる |
| **3** | 端末内履歴＋スプレッドシートへのチェック行追記（7-2/7-3） | 0.5日 | 全体像が見える |
| **4** | アミーゴ壁打ちモード（消し込みリスト・コピー・やさしい言葉） | 1〜2日 | アミーゴに渡せる |
| **5** | 再チェックの差分表示（前回→今回で何が直ったか） | 1日 | 往復がラクになる |

**Phase 1 は単独で出せる。** タブも履歴も無くても、
いまのトップ画面の結果の下にFB文生成を足すだけで動く。
**最短で価値が出るのはここ。**

## 11. 残りの確認したいこと

1. **アミーゴの名前はどこで入れる？** チェック前に「アミーゴ [   ]」を置く案（4-1）でよいか。
   それとも毎回入れるのは面倒で、選択式（登録したアミーゴから選ぶ）がよいか
2. **「2通に分ける」は要るか。** くわしい(500字)をLINEで送るとき、
   「①あいさつ＋よかったところ」「②直してほしいこと」に割る機能
3. **企画名はポスターから自動で取る前提でよいか**（`/api/survey` は既に `event.workshopName` を取っている。
   チェック側でも同じことをする）
4. スプレッドシート連携（7-3）は本番で有効になっているか。
   `SHEETS_WEBHOOK_URL` が未設定だと、この道は使えない

## 付録C. メール送信について

今回は**LINEのみ**。メールで送りたくなった場合の差分だけ記録しておく:
件名が要る／「お疲れさまです」から始める／署名欄／改行は少なめ／絵文字なし。
`channel: "mail"` を `/api/feedback` に足せば、プロンプトの分岐だけで対応できる。
